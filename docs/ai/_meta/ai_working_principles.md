## 🚀 Принцип 0: Процедура активации в новой сессии

Когда начинается новая сессия, ИИ должен:

1. Прочитать `BOOT.md` в корне репо (точка входа)
2. **Прочитать `NEXT_STEPS.md` в корне репо** — краткий обзор «что открыто и что следующее» (1 страница, быстрый orientation)
3. Прочитать **этот файл** (`ai_working_principles.md`) — понять, как работать
4. Прочитать `session_memory.md` — понять, где мы
5. Прочитать `project_status.md` — понять, что сделано
6. Прочитать `open_questions.md` — понять, что требует решения (полный реестр с DASHBOARD в начале)
7. Прочитать `decision_log.md` (последние 3-5 записей) — понять, почему так
8. Прочитать `reasoning_log.md` — понять ход рассуждений (если нужен контекст)
9. Углубиться в конкретные домены при необходимости (`02_world/`, `06_technology/` и т.д.)
10. Кратко изложить пользователю: где мы, что дальше
11. Спросить: «Продолжаем с того-то? Или есть новые приоритеты?»

Пользователь активирует ИИ промптом-шаблоном (см. `session_memory.md` → «Шаблон промпта для активации»).

### ⚠️ Важно про NEXT_STEPS.md

`NEXT_STEPS.md` — это **живой файл**, который обновляется при каждом изменении статуса вопроса. Если вопрос закрыт или приоритет изменён — нужно обновить и `NEXT_STEPS.md`, и `open_questions.md` (DASHBOARD + полный список).

## 🎯 Принцип 1: Лови тренды, не букву

Пользователь даёт **концептуальные примеры** для иллюстрации общих принципов. Не воспринимай их буквально — извлекай **мета-принцип**, который применяется ко всему множеству случаев.

### Пример из практики

Пользователь сказал: «Медь плавится при 700°C, кирпич держит 800-900°C → можно плавить медь. Железо требует 1500°C → нет материала для печи → нет плавки железа.»

**Буквальное понимание (❌ неправильно)**: добавить только физико-химические предпосылки как отдельную категорию, сфокусированную на металлургии.

**Трендовое понимание (✅ правильно)**: это иллюстрация общего принципа — «технология A зависит от развития технологии B». Применять ко ВСЕМ технологиям, не только к металлургии. Плавка железа = один из десятков примеров.

### Как применять

Когда пользователь даёт пример:
1. Спроси себя: «Какой **принцип** он иллюстрирует?»
2. Обобщи принцип на все подходящие случаи
3. Не зацикливайся на конкретных деталях примера
4. Если есть сомнения — лучше спросить «я правильно понял: принцип в том-то?» чем фиксировать буквальное понимание

## 🎯 Принцип 3: Записывай ход рассуждений

Пользователь хочет, чтобы при обрыве сессии можно было прочитать нужный файл и **вспомнить ход мыслей**. Поэтому:

- ✅ Фиксируй не только решение, но и **ход рассуждений**, который к нему привёл
- ✅ Объясняй, **почему** решено так, а не иначе
- ✅ Указывай, какие **альтернативы** рассматривались
- ✅ Помечай **открытые подвопросы** для будущей проработки

Для этого служат два файла:
- `decision_log.md` — журнал концептуальных решений (что решили)
- `reasoning_log.md` — журнал рассуждений (как мы к этому пришли, ход мыслей)

## 🎯 Принцип 9: Бесконечное развитие

Нет верхней границы по эпохам. Игрок играет столько, сколько хочет — 1000, 5000, 10000 лет. Эпохи — это **описание текущего уровня**, не временные рамки. Каждая цивилизация создаёт свою эпоху своим технологическим, культурным, экономическим (и прочим) развитием.

### Что это значит на практике

1. **Включаем ВСЕ исторически возможные технологии** — даже «поздние» (алюминий, электричество, пластик, атом), но с правильными предпосылками
2. **Каждая технология имеет список предпосылок** — без их выполнения нельзя «открыть»
3. **Цепочки технологий длинные** — от древесного угля (неолит) до атома (20 в.) — путь в 12000 лет
4. **Игрок сам решает, докуда развиваться** — можно остаться в палеолите (по выбору) или дойти до пластика
5. **Эпохи как состояние, не календарь** — «каменный век», «бронзовый», «железный», «индустриальный» — это маркеры, не насильно навязанные рамки

### Ключевые «бутылочные горлышки» для переходов между эпохами

| Переход | Нужно |
|---|---|
| Медь → Бронза | Источник олова (касситерит) |
| Бронза → Железо | Огнеупоры (шамот) + графит (тигли) + древесный уголь |
| Железо → Сталь | Кокс (←каменный уголь) + домна + огнеупоры |
| Сталь → Индустриализация | Паровая машина (Ньюкомен, 1712; Уатт, 1769) |
| Индустриализация → Электричество | Магнит + медь → генератор (Фарадей, 1831) |
| Электричество → Алюминий | Бокситы + криолит + электролиз (Холл-Эру, 1886) |
| Алюминий → Электронная эпоха | Полупроводники (Si, Ge — 20 в.) |
| → Ядерная энергия | Уран + графит + теория атома (1942) |

### Принцип для дизайна

При проектировании дерева технологий:
- Каждая технология имеет **список предпосылок** (знания, ресурсы, материалы, технологии)
- Нет «искусственного деления на эпохи»
- Игрок сам решает, куда идти
- Все пути возможны, если выполнены предпосылки

**См.**: [06_technology/prerequisites.md](../06_technology/prerequisites.md), [06_technology/processes.md](../06_technology/processes.md), [02_world/processed_materials/](../02_world/processed_materials/)

## 🔗 Принцип 10: Обязательная связность (критический)

Каждый элемент в каталогах (ресурс, материал, процесс, изделие) **ОБЯЗАН** иметь связи с другими элементами. **Никаких «висящих» элементов.**

### Правило

При добавлении нового элемента (в любом каталоге: resources, processed_materials, items, processes, и т.д.) ИИ **обязан**:
1. **Описать элемент** (состав, свойства, процесс, и т.д.)
2. **Указать входящие связи** — из чего сделан / что нужно для него:
   - Сырьё (→ путь к ресурсу)
   - Процесс (→ путь к processes.md)
   - Предпосылки-технологии (→ путь к tech_tree.md)
3. **Указать исходящие связи** — для чего нужен / что делается из него:
   - Материалы (→ путь к processed_materials/)
   - Изделия (→ путь к items/)
   - Технологии (→ путь к tech_tree.md)
4. **Указать альтернативы** — что можно использовать вместо (если есть)
5. **Указать роль** — «бутылочное горлышко»? Критично для какой-то цепочки? Или рядовой элемент?
6. **Проверить**, что элемент не «висит» — имеет хотя бы одно применение

### Если у элемента НЕТ применения

- Либо **создать применение** — добавить его в какую-то цепочку
- Либо **удалить элемент** — он не нужен в игре

### Принудительность

Это правило работает **«на автомате»** — при добавлении нового ИИ обязан прописать связи. Не «по желанию», а **обязательно**. Если ИИ забывает — это баг (нарушение принципа).

### Шаблон для нового элемента

```
### Название

**Категория**: 🟢/🟡/🔴 (для ресурсов) или тип (для материалов/изделий)
**Состав**: ... (что это, химический/физический состав)
**Процесс**: ... (какой процесс нужен — для материалов, см. processes.md)

**Входящие связи** (из чего делается / что нужно):
- сырьё1 → [путь к файлу]
- процесс1 → [путь к processes.md]
- технология1 → [путь к tech_tree.md]

**Исходящие связи** (для чего нужен / что делается из него):
- материал1/изделие1 → [путь]
- технология1 → [путь к tech_tree.md]

**Альтернативы** (что можно использовать вместо):
- альтернатива1 → [путь]

**Роль**: бутылочное горлышко? критично? рядовой?
```

## 🔍 Принцип 11: Валидация связей

Периодически (после больших изменений в каталогах) проводить **валидацию** — сканировать все каталоги и проверять, что каждый элемент имеет хотя бы одну входящую и одну исходящую связь.

### Как проводить валидацию

**В концептуальной стадии (сейчас):**
1. Визуально проверить — есть ли у каждого элемента раздел «Связи»
2. Пройтись по всем каталогам, найти «висящие» элементы
3. Для каждого висящего — либо добавить применение, либо удалить

**В технической стадии (когда код):**
1. Скрипт-валидатор (Python) парсит все .md файлы каталогов
2. Извлекает каждый элемент
3. Проверяет наличие раздела «Входящие связи» и «Исходящие связи»
4. Если нет → ошибка → нужно исправить
5. CI/CD правило: при коммите запускается валидатор, не пускает коммит с висящими элементами

### Когда проводить

- После добавления **большой группы** новых элементов (≥10)
- После **реструктуризации** каталогов
- Перед **переходом к коду** (полная валидация всего)

### Документ валидации

Результат валидации — отчёт в `_meta/validation_log.md` (будет создан):
- Дата валидации
- Кол-во проверенных элементов
- Кол-во висящих
- Что исправлено

## 🔒 Принцип 12: Сначала дыры, потом разработка

Пока не закрыты все известные дыры и баги — **дальше не идём**. Сначала закрываем все известные проблемы, потом продолжаем разработку. **96% — недостаточно. Нужно 100% связей и всегда.** Если найдена дыра — она приоритет №1.

### Правило

1. Перед началом новой работы — проверить, нет ли известных дыр (через `validate_dependencies.py` и аудит принципов)
2. Если есть висящие элементы → **сначала исправить** (добавить связи или удалить элемент)
3. Если есть несоответствие принципам → **сначала исправить**
4. Только после 100% чистоты → продолжать разработку

### Применение

- **Валидация связей** (Принцип 11) → цель: **0 висящих**, не «приемлемо 3%»
- **Аудит принципов** → все принципы 0-13 должны быть соблюдены
- **Синхронизация** → docs/ai/ и docs/user/ должны быть синхронизированы (Принцип 5)
- Если обнаружена дыра во время работы — **остановиться и исправить**, потом продолжать

## 🧊 Принцип 13: Палеолитный тест

Каждая механика должна **либо работать в 10 000 до н.э. (стартовый год), либо иметь явное условие включения** (технология/событие). Вопрос, который нужно задавать при проектировании каждой новой механики: **«с чего это начинается в палеолите?»**

### Правило

При добавлении новой механики (или заимствовании из существующих игр) ИИ обязан:

1. **Проверить**: работает ли механика в палеолите (10 000 до н.э.)?
2. **Если да** → механика доступна с первого хода
3. **Если нет** → указать **явное условие включения**:
   - Технология (например, зонирование через инфраструктуру требует T-020 деревообработки)
   - Событие (например, рабство активируется при войне + социальной сложности)
   - Эпохальный переход (например, фракция «учёные» появляется в античности)
4. **Если условие не определено** → механика не принимается (это «висящая» механика, нарушающая Принцип 10)

### Применение

- **Проверка новых механик** — каждый раз при добавлении новой системы
- **Чек-лист для аудита** — добавить в `scripts/validate_dependencies.py` ручную проверку: «с чего это начинается в 10 000 до н.э.?»
- **Связь с Принципом 9** (бесконечное развитие) — эпохи = состояние, не календарь; но каждая механика должна иметь точку входа

### Примеры из дискуссии (раунды 02-06)

| Механика | Палеолитный аналог | Условие включения |
|---|---|---|
| Зонирование через инфраструктуру | Природные + объявленные якоря | Построенные якоря — по технологиям |

## 📚 Принцип 14: Тест на один справочник

При добавлении новой классификации/таксономии **проверить, не существует ли уже аналогичной в проекте**. Если существует — **не создавать параллельную, а подключить существующую**.

### Правило

Вопрос, который нужно задавать при добавлении новой классификации: **«не заведён ли второй справочник для того, что уже описано?»**

При добавлении новой таксономии/классификации ИИ обязан:

1. **Проверить** — есть ли уже в проекте классификация для этой сущности?
2. **Если есть** — подключить существующую, не создавать параллельную
3. **Если нет** — создать, но явно указать, что это новый справочник

### Применение

- **Проверка новых механик** — каждый раз при добавлении новой системы, использующей классификацию
- **Четвёртая методологическая проверка** (в дополнение к палеолитному тесту, двойной бухгалтерии, видимости)
- **Связь с Принципом 10** (обязательная связность) — параллельный справочник = нарушение связности

### Примеры из дискуссии (вторая волна, раунды 09-11)

| Вопрос | Параллельный справочник | Решение |
|---|---|---|
| Q-007 Стартовый пакет | 8 типов еды рядом с 8 архетипами GDD | Еда выводится из архетипа |
| Q-009 Блокировки | 4 блокировки рядом с ползунками и фракциями | Диагноз через существующие системы |
| Q-015 Стадии | 6 стадий рядом с деревом технологий | Стадия-отражение, не рычаг |
| Q-008 Альт. пути | Источники калорий по архетипам | Вычисляемые доли из полей гекса |

### Эффективность

Проверка выявила дефекты в **3 вопросах из 7** второй волны — каждый четвёртый вопрос содержал параллельный справочник. Самая продуктивная из 4 проверок по соотношению «усилие/результат» (по оценке Модели B).
