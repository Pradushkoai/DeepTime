# T-007: Производительность — Спецификация

> 📋 **Спецификация T-007** — профиль нагрузки, целевые метрики, оптимизации. 30 000+ агентов с индивидуальностью — главный технический риск проекта (аудит Модели B).
>
> **Принцип**: измерять перед оптимизировать. Сначала профиль, потом узкие места, потом оптимизации.

---

## 🎯 Обзор

GDD §19 обещает «30 000+ граждан с индивидуальностью». Аудит Модели B отметил: «SoS — ~50 ресурсов; DF — ASCII-рендер; W&R — без граждан-личностей; ML — один регион. Ни один из четырёх референсов не тянул такого объёма».

Эта спека:
1. Определяет целевые метрики (FPS, память, load time)
2. Оценивает профиль нагрузки по системам
3. Идентифицирует узкие места
4. Предлагает оптимизации
5. Определяет бенчмарки для проверки

## 🚨 Узкие места (прогноз)

### 1. CitizenActionSystem — utility score

**Проблема**: 100 граждан × 1/сек × вычисление utility для 16 actionTypes × 5-10 параметров = ~16 000 ops/сек.

**Решение**:
- Кешировать utility score (не пересчитывать, если параметры не изменились)
- Dirty flag: помечать гражданина «dirty» при изменении Needs/Skills/Editions
- Parallel by citizen (Unity Jobs System)

### 2. VisibilitySystem — 64 800 гексов

**Проблема**: если тикать все 64 800 гексов 1/сек — 64 800 ops/сек.

**Решение** (T-003):
- Тикать только Observed гексы (~100)
- Остальные — по событию (разведгруппа вошла → обновить)
- InMemory гексы — устаревают лениво (при просмотре игроком)

### 3. Save/Load — 13 МБ snapshot

**Проблема**: сериализация 30 000 граждан может занять секунды.

**Решение**:
- Parallel serialization (Unity Jobs)
- Не сериализовать статичные данные (каталоги, гекс-рельеф)
- Сериализовать только динамические компоненты (Health, Needs, Position, Loyalty)

### 4. Рендер 100 граждан с анимацией

**Проблема**: skeletal animation 100 граждан × 60 FPS = 6 000 анимаций/сек.

**Решение**:
- GPU skinning (на GPU, не CPU)
- LOD для анимаций: близкие — 30 fps, средние — 15 fps, дальние — points
- Анимации только для граждан в кадре (culling)

### 5. Pathfinding для 100 мигрантов

**Проблема**: A* по гекс-сетке 64 800 — дорого.

**Решение**:
- Pre-computed flow fields для популярных маршрутов
- Hierarchical pathfinding: гекс → локальная карта → путь
- Кеширование: один мигрант за другим по тому же маршруту — переиспользуем

### 6. EventSystem — проверка триггеров

**Проблема**: 50+ триггеров × 1/ход = 50 проверок/ход. На темпе «эпохи» (1-5 лет за ход) — нормально. На темпе «вождя» (1 сезон) — много ходов.

**Решение**:
- Триггеры с условиями «дешёвой проверки» (health == 0) — всегда
- Триггеры со «сложной проверкой» (AICivArc progress) — раз в 5 ходов
- Dirty flags: проверять только если состояние изменилось

## ⚙️ Оптимизации (план)

### ECS-оптимизации

1. **Component chunking** — Unity DOTS автоматически группирует entities с одинаковыми archetype'ами
2. **Burst compilation** — C# → IL → optimized native code (SIMD)
3. **Job System** — параллельные системы на нескольких ядрах
4. **Cache-aware data layout** — POD в contiguous массивах

### Рендер-оптимизации

1. **GPU Instancing** — тысячи объектов в одном draw call
2. **LOD (3 уровня + impostors)**
3. **Occlusion culling** — не рисовать скрытое
4. **HLOD** — кварталы как одна модель на дистанции
5. **Culling по камере** — только видимое

### Memory-оптимизации

1. **Pooling** — переиспользование entities (не Create/Destroy, а Activate/Deactivate)
2. **Arena allocation** — большие блоки вместо мелких аллокаций
3. **String interning** — для имён (FixedString64 вместо string)
4. **Asset bundles** — ленивая загрузка текстур/мешей

### Network-оптимизации (для Q-018)

1. **Delta compression** — только изменения в input log
2. **Predictive movement** — клиент предсказывает, сервер подтверждает
3. **Lag compensation** — rewind state для проверки попаданий

## 📐 Бенчмарки

### Бенчмарк 1: Стартовый поселок (50 граждан)

- 50 граждан × 1 тик/сек = 50 ops/сек
- 5 зданий × 1 тик/мин = 0.08 ops/сек
- Ожидаемый FPS: 60+ (no constraints)

### Бенчмарк 2: Город (5 000 граждан)

- 5 000 граждан (100 индивидуальных + 4 500 в когортах)
- 100 × 1/сек + 4 500 / 9 когорт × 1/мин = 100 + 50 = 150 ops/сек
- Ожидаемый FPS: 60 (предел — рендер 100 граждан)

### Бенчмарк 3: Столичная империя (30 000 граждан)

- 30 000 (100 индивидуальных + 29 900 в когортах)
- 100 × 1/сек + 29 900 / 9 × 1/мин = 100 + 55 = 155 ops/сек
- Ожидаемый FPS: 60 (предел — рендер 100 граждан + глобальная карта)

### Бенчмарк 4: Стресс-тест (100 000 граждан)

- 100 000 (100 индивидуальных + 99 900 в когортах)
- 100 × 1/сек + 99 900 / 9 × 1/мин = 100 + 185 = 285 ops/сек
- Ожидаемый FPS: 30-60 (зависит от CPU)

> Бенчмарк 4 — сверхцелевой. Если работает — у нас есть запас.

## 📈 Метрики для профайлинга

### Runtime метрики

```csharp
public static class PerformanceMetrics {
    public static float Fps;                    // кадры/сек
    public static float SimTimeMsPerTurn;       // ms симуляции на ход
    public static float RenderTimeMsPerFrame;   // ms рендера на кадр
    public static long MemoryUsedBytes;         // RAM
    public static long GpuMemoryUsedBytes;      // VRAM
    public static int EntityCount;              // всего ECS-entities
    public static int ActiveSystemsCount;       // активных систем
}
```

### Метрики для отладки (в Editor)

- **Performance Overlay** — FPS, ms/frame, entity count (как в RimWorld)
- **System Profiler** — сколько ms каждая система занимает
- **Memory Profiler** — breakdown по типам данных
- **ECS Query Profiler** — сколько времени на запросы
